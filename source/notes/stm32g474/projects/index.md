## 1. 先按职责拆分

不必把一个设备的全部功能塞进 main.c。更实用的做法是围绕数据流拆分模块：采集模块产出样本，波形模块提供激励，算法模块产出分析结果，测量模块负责量程与校准，设备模块处理通信与交互。每个模块都应有清楚的输入、输出和初始化接口。

| 模块 | 主要职责 | 最小验收 |
| --- | --- | --- |
| 数据采集 | 定时触发、ADC、DMA 缓冲 | 采样率正确，连续运行不丢块 |
| 波形输出 | DDS、DAC、外部激励 | 频率、幅值、相位可重复设置 |
| 信号处理 | FFT、滤波、相关与参数估计 | 已知输入得到正确数值 |
| 测量控制 | 扫频、量程、校准、异常判断 | 结果带有效性与校准状态 |
| 设备交互 | 传感器、显示、按键、通信 | 不阻塞实时数据链 |

## 2. 让配置和运行状态分开

采样率、缓冲长度、阈值、校准系数等会变化的内容应集中放在配置结构里；计数器、当前量程、错误标志等则属于运行状态。配置说明“如何运行”，状态说明“现在运行得怎样”。两者分开后，更容易保存参数，也便于在串口或屏幕上做诊断。

~~~c
typedef struct {
    uint32_t sample_rate_hz;
    uint16_t block_size;
    float input_scale;
} CaptureConfig;

typedef struct {
    uint32_t completed_blocks;
    uint32_t overrun_count;
} CaptureStatus;
~~~

### 接口要表达失败，而不只表达成功

模块接口除了参数，还应说明返回状态。比如采集模块可以区分“没有新数据”“拿到一块数据”“发生过载”，而不是只返回一个裸指针。调用方据此决定是继续计算、等待下一帧，还是把本次结果标为无效。

~~~c
typedef enum {
    CAPTURE_WAITING,
    CAPTURE_READY,
    CAPTURE_OVERRUN
} CaptureResult;

CaptureResult Capture_GetBlock(const uint16_t **samples,
                               uint16_t *count);
~~~

接口名称也尽量使用动词加对象，例如 Capture_Start、Dds_SetFrequency、Analyzer_Process、Meter_GetResult。读者不必翻到实现文件，也能大致判断调用的副作用和调用顺序。

## 3. 给实时链路划清边界

DMA 回调、定时器回调和高优先级中断只做必要工作：切换缓冲区、写标志、记录时间戳。FFT、格式化字符串、屏幕刷新和 Flash 写入都放在主循环或低优先级任务中。

一个简单的判断标准是：某段代码如果执行时间会随数据内容、串口状态或外设响应而显著变化，就不要放进采样回调。把这些不确定工作移出去，系统的抖动会小很多。

## 4. 用最小验证替代整机猜错

1. 先验证时钟、GPIO 和一条串口日志。
2. 单独验证 ADC 或 DAC 的定时器触发与 DMA。
3. 给算法喂入已知测试信号，确认数值结果。
4. 单独验证一条 SPI、I2C 或 UART 事务。
5. 最后把测量、显示和交互接回实时链路。

每一步都留下一个可复现的判据，例如频率、峰值码、寄存器读回值或逻辑分析仪截图。这样当整机出现异常时，可以从最近一次通过的边界开始定位。

## 5. 版本与参数记录

当频率表、滤波器系数或校准数据需要保存时，数据结构应带上魔数、版本号、长度和 CRC。升级固件后，旧数据不匹配就按默认值重新生成，不要勉强解析。参数记录里至少注明单位、采样率和适用量程；同一个数值在不同条件下可能有完全不同的含义。

## 6. 模块完成前的验收清单

- 初始化是否可重复执行，失败时能否返回清楚的错误码。
- 输入是否检查长度、范围、空指针和不支持的配置。
- 实时回调是否有确定的执行上限，是否记录过载次数。
- 停止与重新启动后，DMA、定时器和外设状态是否一致。
- 参数和校准数据是否带版本、单位和校验。
- 是否能在不接入完整系统时完成最小测试。

完成这些检查后，代码不一定“最炫”，但会更容易移植、维护和解释。这正是专题中每一章都在努力建立的共同底座。
